# Agent 记忆系统设计实践

> 基于生产级诊断 Agent 的记忆系统提炼，已脱敏处理。
> 适用场景：需要长期记忆、经验沉淀、自我改进的 LLM Agent 系统。

---

## 一、设计理念

### 1.1 核心原则

```
短期记忆 → 会话状态（内存）
长期记忆 → 结构化持久化（SQLite）
知识库   → 文件系统（人工维护）
```

三层分离：**记忆不放在代码仓库，知识不混入记忆，会话不过度持久化**。

### 1.2 为什么不用向量数据库

第一版采用纯结构化字段匹配，不依赖 embedding：

| 考虑 | 说明 |
|---|---|
| **可解释性** | 每条记忆的匹配理由可追溯（命中哪个字段、得分多少） |
| **零依赖** | 不需要 embedding 服务、向量数据库，部署简单 |
| **可调试** | SQLite 直接打开看，不需要额外工具 |
| **够用** | 领域内术语相对固定，字段匹配覆盖大部分场景 |
| **可升级** | embedding 接口预留，未来可平滑切换 |

## 二、记忆分类

系统定义三类记忆，各有不同的生命周期和用途：

### 2.1 诊断经验（Experience）

| 属性 | 说明 |
|---|---|
| **用途** | 记录每次诊断的完整过程，供后续相似问题参考 |
| **存储** | SQLite `experience` 表 |
| **生命周期** | 长期保留，按 recency 衰减 |
| **子类型** | `success`（成功经验）/ `anti_lesson`（反面教训） |

**记录字段**：

| 字段 | 说明 |
|---|---|
| symptom | 故障现象描述 |
| task_status | 任务状态（如"下载阶段""安装失败"等） |
| diagnosis_summary | 诊断结论摘要 |
| key_findings | 关键证据列表（JSON） |
| lesson | 经验教训 |
| tags | 分类标签（JSON） |
| tools_used | 使用的工具列表（JSON） |
| confidence | 置信度 |
| source_vin | 来源车辆标识 |

### 2.2 诊断方法（Method）

| 属性 | 说明 |
|---|---|
| **用途** | 记录"用什么工具查什么数据→得出什么结论"的方法模式 |
| **存储** | SQLite `method` 表 |
| **生命周期** | 长期保留，有 proven 晋升机制 |
| **特点** | 只有被反复验证的方法才会晋升为 proven |

**记录字段**：

| 字段 | 说明 |
|---|---|
| trigger | 触发场景（任务状态/故障类型） |
| trigger_keywords | 触发关键词（JSON） |
| tool | 使用的工具名称 |
| what_to_check | 检查什么 |
| interpretation | 如何解读结果 |
| occurrence_count | 出现次数 |
| proven | 是否已验证（0/1） |
| positive_feedback | 正面反馈次数 |
| rethink_feedback | 反思反馈次数 |

### 2.3 术语纠正（Correction）

| 属性 | 说明 |
|---|---|
| **用途** | 记录用户纠正过的术语/概念错误 |
| **存储** | SQLite `correction` 表 |
| **生命周期** | 长期保留，按纠正次数加权 |
| **注入方式** | Top-K 注入 LLM System Prompt |

## 三、检索策略

### 3.1 混合评分公式

每条记忆被召回时，按以下公式计算相关性得分：

**经验评分**：

```
Score = 0.55 × CosineSim + 0.30 × FieldBonus + 0.05 × Usage + 0.10 × Recency
```

- **CosineSim**：语义相似度（embedding 可用时启用，不可用时权重归零）
- **FieldBonus**：字段匹配加分（task_status 匹配 +0.50，有标签 +0.33，成功经验 +0.17）
- **Usage**：使用次数对数归一化 `min(log(1+use_count)/5, 1.0)`
- **Recency**：时间衰减 `exp(-0.01 × days)`

**方法评分**：

```
Score = 0.50 × CosineSim + 0.30 × FieldBonus + 0.20 × ProvenBonus
```

- **ProvenBonus**：已验证方法 +1.0，未验证 0

### 3.2 Embedding 降级策略

当 embedding 不可用时，自动降级为纯字段匹配：

```
embedding 可用:  w_cos=0.55, w_field=0.30, w_usage=0.05, w_recency=0.10
embedding 不可用: w_cos=0.00, w_field=0.85, w_usage=0.05, w_recency=0.10
```

**降级去重回退**：embedding 不可用时，用关键词重叠率判断相似度：

```
overlap = |new_kw ∩ exist_kw| / max(|new_kw|, |exist_kw|)
if overlap > 0.6 → 视为重复
```

### 3.3 召回注入

每次诊断时，自动检索并注入到 sub-agent 的上下文中：

```python
context = {
    "prior_experiences": [  # 最多 3 条经验
        {"id": "exp-xxx", "symptom": "...", "lesson": "...", ...}
    ],
    "diagnostic_methods": [  # 最多 5 条方法
        {"id": "mtd-xxx", "tool": "...", "proven": True, ...}
    ],
    "terminology_corrections": [  # Top-K 纠正
        {"wrong_term": "...", "correct_term": "...", "context": "..."}
    ],
}
```

每条经验/方法都附带 `id`，可追溯到具体来源。

## 四、写入门控

### 4.1 显式触发机制

记忆写入不是每次诊断都执行，而是需要用户**显式触发**：

- 用户在消息中包含特定关键词（如 `#otalearn`）→ 门控开启
- 三个消息通道（CLI / API / IM）统一走同一门控

### 4.2 为什么需要门控

| 不开门控的问题 | 说明 |
|---|---|
| 记忆污染 | 非诊断对话（闲聊、测试）被误存为经验 |
| 噪音积累 | 低质量诊断结果拉低整体检索效果 |
| 隐私风险 | 敏感对话被持久化 |

### 4.3 自动提取的内容

门控开启后，自动从诊断结果中提取：

1. **经验**：诊断结论、关键证据、建议操作 → `save_experience()`
2. **方法**：仅 confidence ≥ 90 且 evidence 标注为 `confirmed` + `tool_return` → `save_method()`
3. **纠正**：检测 LLM 回复中的纠正标记 `<!--CORRECTION_START-->...<!--CORRECTION_END-->` → `save_correction()`

## 五、质量保障

### 5.1 元认知审计

诊断完成后，程序化检查红旗信号：

| 审计项 | 触发条件 | 严重程度 |
|---|---|---|
| **assumed_key_evidence** | 关键证据依赖假设而非事实 | 🔴 高 |
| **high_confidence_thin_evidence** | 置信度 ≥ 80% 但 confirmed 证据 < 2 条 | 🟡 中 |
| **all_hypotheses_rejected** | 所有假设均被排除 | 🔴 高 |
| **untagged_evidence** | 证据未标注认知置信度 | 🟢 低 |

审计结果标记在诊断结果中但不自动重跑（避免倍增耗时），由上层决定是否追加验证。

### 5.2 经验分类

根据审计结果自动分类：

- 无红旗信号 → `success`（成功经验）
- 有关键证据假设 → `anti_lesson`（反面教训）

反面教训同样存入经验库，但 subtype 标记为 `anti_lesson`，检索时可区分。

### 5.3 方法验证机制（Proven）

方法从"初步记录"到"已验证"需要满足：

```
occurrence_count ≥ 3  AND  (positive_feedback - rethink_feedback) ≥ 1
```

| 状态 | 含义 | 检索权重 |
|---|---|---|
| 未 proven | 尚未被充分验证 | 0 |
| **proven** | 反复出现且有正面反馈 | **+1.0** |

proven 方法在检索评分中占 20% 权重，确保已验证的方法优先被召回。

## 六、会话状态记忆

### 6.1 会话级追踪

每次会话维护以下状态（内存，不持久化）：

| 追踪项 | 说明 |
|---|---|
| 当前车辆标识 | 当前讨论的车辆 |
| 当前版本 | 车辆当前版本号 |
| 目标版本 | 升级目标版本 |
| 最近任务 ID | 最近诊断的任务编号 |
| 最近诊断 | 最近一次诊断结果缓存 |
| 待确认操作 | 待确认的写操作 |

### 6.2 被排除假设管理

Agent 在诊断过程中会提出多个假设，验证后排除的假设被记录：

```
每条假设记录：
  - hypothesis: 假设内容
  - refuted_by: 排除依据
  - refutation_count: 被排除次数（跨车辆累积）
  - last_seen: 最后排除时间
```

**跨车辆保留**：切换车辆时，已排除假设不清空（排除经验有价值）。

**加权淘汰**：最多保留 30 条，超限时淘汰 refutation_count 最低 + 最旧的。

**注入诊断上下文**：每次诊断时，Top-5 已排除假设注入 sub-agent，避免重复犯错。

## 七、反馈闭环

### 7.1 双层反馈

| 层级 | 触发方式 | 存储 |
|---|---|---|
| **诊断级** | 用户对诊断结果点赞/踩 | `vote_log` 表（SQLite） |
| **方法级** | 点赞时自动关联：对本次诊断提取的方法 + positive_feedback | `method` 表 |

### 7.2 反馈链路

```
用户点赞
  → 记录 vote_log
  → 查找本次诊断提取的 method_ids
  → 对每条 method 执行 record_method_feedback(mid, "positive")
  → 重新计算 proven 状态
```

用户踩不会自动触发负反馈（避免误伤），但 vote_log 记录可后续分析。

---

## 八、纠正检测

### 8.1 自动检测机制

LLM 回复中嵌入结构化纠正标记：

```
回复文本...
<!--CORRECTION_START-->
{"wrong_term": "推送", "correct_term": "下发", "context": "OTA升级场景"}
<!--CORRECTION_END-->
```

### 8.2 纠正处理

- 首次纠正 → 新建记录（correction_count=1）
- 相同 wrong_term 再次纠正 → 合并（correction_count+1，更新 correct_term）
- 按 correction_count 降序，Top-K 注入所有后续 LLM prompt

### 8.3 注入示例

```
## 记忆（用户纠正）
以下是用户纠正过的术语，你**必须**使用正确的表述，不得再犯：
- ❌ 推送 → ✅ 下发（OTA升级场景）
- ❌ 刷写 → ✅ 烧录（ECU升级场景）
```

## 九、数据迁移

### 9.1 旧格式兼容

系统启动时自动检测旧格式数据（JSON 文件），迁移到 SQLite：

```
1. 检测旧 index.json 是否存在
2. 遍历旧记录，按类型插入对应 SQLite 表
3. 跳过已存在的记录（去重）
4. 迁移完成后重命名旧文件为 .migrated
```

### 9.2 迁移安全

- 事务安全：迁移在同一个 commit 中完成
- 幂等：已迁移的记录不会重复插入
- 回滚：迁移失败不影响现有数据

## 十、架构总结

### 10.1 数据流全景

```
用户消息
  │
  ├─→ 状态提取 → SessionState（VIN/版本/任务ID）
  │
  ├─→ 门控判断 → #otalearn 关键词检测
  │
  ├─→ 记忆检索 → 混合评分 → 经验 + 方法 + 纠正
  │       │
  │       ├─→ 注入 Orchestrator prompt（纠正）
  │       └─→ 注入 Diagnostic Agent prompt（经验+方法+纠正）
  │
  ├─→ 诊断执行 → Sub-Agent
  │
  ├─→ 元认知审计 → 红旗检测 → success/anti_lesson 分类
  │
  ├─→ 记忆写入（门控开启时）
  │       ├─→ save_experience（去重+合并）
  │       ├─→ save_method（仅 confidence≥90）
  │       └─→ parse_correction（检测纠正标记）
  │
  └─→ 反馈收集
          ├─→ 点赞/踩 → vote_log
          └─→ 点赞 → method.positive_feedback → 重算 proven
```

### 10.2 关键设计决策

| 决策 | 选择 | 原因 |
|---|---|---|
| 存储引擎 | SQLite | 零依赖、可调试、事务安全 |
| 检索方式 | 混合评分（字段匹配为主） | 可解释、不需要 embedding 服务 |
| 去重策略 | 相似度 > 0.85 合并 | 避免记忆膨胀 |
| 写入门控 | 显式关键词触发 | 防止记忆污染 |
| 方法验证 | 3次出现 + 正反馈 > 反思 | 只有反复验证的方法才晋升 |
| 假设排除 | 跨车辆保留 + 计数淘汰 | 扩大排除经验的价值 |
| 纠正注入 | 加权 Top-K 注入 prompt | 高频纠正优先，避免 prompt 膨胀 |

### 10.3 适用场景

这套设计适合以下场景的 Agent 系统：

- 领域相对固定，术语/概念有限
- 需要从每次交互中积累经验
- 诊断/分析类任务，有明确的成功/失败判定
- 多轮对话，需要跨会话记忆
- 对部署复杂度敏感，不希望引入向量数据库等额外依赖

### 10.4 不适用场景

- 开放域对话（领域太广，字段匹配不够）
- 需要跨领域语义联想（缺少 embedding 能力）
- 短期临时任务（不需要长期记忆）
- 对实时性要求极高（SQLite 同步写入）

## 十一、改进方向

| 方向 | 当前状态 | 建议 |
|---|---|---|
| **负反馈持久化** | 假设排除只在内存，不写回 SQLite | experience 加 `refuted_count` 字段，检索时扣分 |
| **Badcase 飞轮** | 无定期回放机制 | 从 anti_lesson 中抽样，用新 prompt 重跑，对比结果 |
| **准确率度量** | 原始日志有，但无聚合 | 加全局准确率 = like/(like+dislike)，按维度切分 |
| **反模式聚类** | 无 | 对 anti_lesson 按 task_status 聚类，发现系统性缺陷 |
| **Embedding 恢复** | 接口已预留，当前禁用 | 在有 embedding 服务后启用，切换到语义+字段混合模式 |
| **记忆衰减** | recency 仅 10% 权重 | 加主动衰减：超过 N 天未使用的经验自动归档 |
