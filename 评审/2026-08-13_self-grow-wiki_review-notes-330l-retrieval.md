## 一、事件经过

1. 用户问 M-900iB/330L 与 280L 的速度差异
2. Hermes agent 检索后回答: **"M-900iB/330L 不存在"** (知识库未检索到 330L 规格数据)
3. 人工核验: B-83684CM_05.PDF §3.1 规格一览表 (PDF 页 36-37) 白纸黑字有 **M-900iB/330L 完整规格**
   (330kg、J1-J6 速度 100/85/85/90/85/165°/s); 手册改版履历 (页 159) 记录 2020-05 追加 330L

## 二、调查证据链

| 环节 | 发现 |
|---|---|
| 手册原文 | ✅ 有 330L 规格 (B-83684CM_05.PDF 页 37) |
| 蒸馏数据 `chunks_filtered.json` | 覆盖 330L 的 8 块均为搬运/安装/可动范围, **无规格表页 (p37)** — 蒸馏稀疏采样恰好跳过 |

| 检索复现 `retrieve("M-900iB 330L 比 280L 慢多少")` | top-10 **无规格表** — 全是搬运页/连接图/型号清单 (分数 0.98, 几乎无区分度) |

## 三、根因分析 (三层)

### 1. 环境根因 (真正的病根): BM25 依赖缺失
- `rag_core.py` 的 BM25 混合检索需要 `rank_bm25` + `jieba`
- **两者均未安装** → `_BM25_AVAILABLE = False` → `BM25Index._ensure_index()` 直接返回 False
- → BM25 索引永不加载 (缓存 615MB pkl 存在但用不上) → **检索静默降级为纯向量路径** (无任何告警/日志提示降级)
- 330L 规格表是表格文本: 向量语义分低 (embedding 对表格不敏感), 只有 BM25 精确命中 "330L/最大动作速度" 才能召回 → 纯向量路径下永远无法召回

### 2. 检索链路放大缺陷 (修复后暴露/加固)
- **variant 兜底用 `$contains`**: ChromaDB FTS 把 "330L" 分词为 "330"+"L", 单字符 token "L" 大量误匹配 (31 个候选中多数不含真 "330L")
- **max_per_file=3 挤出**: 型号查询时每文件限 3 chunk, B-83684CM_05.PDF 的搬运页 (向量高分) 占满名额, 规格表被挤出
- **rerank 覆盖分数**: cross-encoder 对表格文本打分低, 覆盖 variant 搜索的高分
- **同一性判断**: `$contains` 返回顺序与相关性无关, limit 截断随机

### 3. 推理根因 (Hermes 侧): 召回 0 ≠ 不存在
- 检索未命中被错误推断为"型号不存在"
- 正确表述应为 "知识库未覆盖 XX 的 [属性]"
- **已落地 prompt 规则 5c** (rag_core.py): 禁否定存在性, 检索缺失时列出已检索片段供人工核实

## 四、修复措施 (commit `4db44ef`)

| 项 | 内容 |
|---|---|
| 依赖 | 安装 `jieba 0.42.1` + `rank-bm25 0.2.2` → BM25 索引恢复 (197,346 chunks) |
| variant 搜索 | 改 BM25 内存索引**精确子串匹配** (替代 `$contains` FTS 误匹配), 保留 $contains 回退 |
| max_per_file | 豁免含型号变体/规格词的 chunk; 改**两遍扫描** (先收集豁免, 再补普通), 避免 break 跳过 |
| 豁免排序 | 含"速度/动作速度"词优先于 score (rerank 覆盖 variant 分数后表格文本分低) |
| 型号搜索触发 | 现有结果无规格内容时仍执行型号精确搜索 (向量高分≠好答案) |

## 六、教训与防范

1. **依赖缺失是隐性故障源**: BM25 降级无告警。→ 依赖应写入文档/requirements, 检索模块启动时校验依赖并显式报错 (而非静默降级)
2. **"检索不到 ≠ 不存在"**: 已用 5c prompt 规则堵住推理侧
3. **表格类内容对向量检索不友好**: 规格表/参数表必须依赖精确匹配 (BM25/全文) 兜底
4. **蒸馏数据与活跃库是两条线**: `chunks_filtered.json` (微调用) 缺失规格表页, 不影响 ChromaDB 灌库 (PDF 直切), 但排查时容易误判"数据缺失"
