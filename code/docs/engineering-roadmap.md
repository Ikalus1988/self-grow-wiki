# RAG 工程收敛与可落地改进路线图

本文整理当前 FANUC 工业知识库从比赛 Demo 走向真实可用工具的工程改进建议。目标不是做包装、平台化或复杂后台，而是用最小成本提升召回率、稳定性和用户关键时刻的使用感知。

## 1. 当前阶段的优先级判断

当前不应把所有优化同时推进。优先级建议如下：

| 优先级 | 问题 | 判断理由 | 最小改进方向 |
| --- | --- | --- | --- |
| P0 | 群聊智能入口可靠性 | 飞书群 + Hermes 是当前最自然入口，但入口异常会直接影响用户关键时刻使用 | 保留 Hermes 智能网关，增加规则兜底、消息落盘和异常可追踪 |
| P0 | 失败不可感知 | 用户不会主动反馈，答错后更可能沉默、追问、换人问或离开 | 用隐式行为与检索信号自动打 `risk_tags` |
| P1 | 答案可信与可执行 | 工业场景里，没出处、不可执行、硬猜测会快速损害信任 | 强制引用、低置信度少答、主动追问型号/截图/上下文 |
| P1 | 工程稳定性与降级 | 用户可以接受慢一点，但不能无响应、卡死、乱答或丢日志 | 增加超时、队列、降级检索和失败日志 |
| P1 | 维护成本 | 如果需要人工翻日志、整理表格，飞轮很难长期转动 | 自动聚合 Top 问题簇，每周只处理少数高价值问题 |
| P2 | 并发能力 | 当前不是第一矛盾，除非已出现多群/多班组同时高频查询 | 先保证 2-4 个并发请求稳定，再压测扩容 |
| P2 | 插件化/跨场景复用 | 有长期价值，但应建立在 FANUC 场景跑稳之后 | 沉淀 RAG Core、领域规则、Agent 网关和质量飞轮 |

## 2. 群聊智能入口：保留 Hermes，但降低单点脆弱性

飞书群入口并不落后。相比网页入口，群聊方式更贴近工程师现场协作：不需要打开新网页，不需要切换上下文，追问、截图、转人工都在同一个工作流里完成。

Hermes 也不只是消息转发器，它可以作为智能网关：

- 判断闲聊、真实知识库查询、追问、反馈和转人工。
- 提取报警码、型号、品牌、设备类型等实体。
- 对用户问题做语义补全和规范化。
- 决定是否调用 RAG，以及调用哪个知识库。
- 低置信度时追问关键上下文。

建议的职责边界：

```text
飞书群消息
  ↓
消息接收层：先落盘，保证可回放
  ↓
Hermes 智能网关：意图判断、上下文补全、工具路由
  ↓
规则兜底层：Hermes 超时/异常时，用报警码、型号、关键词触发 RAG
  ↓
RAG Core API：检索、rerank、生成、引用、risk_tags、query_log
  ↓
飞书群回复：答案、引用、低置信度提示、继续追问建议
```

最小落地任务：

1. 收到飞书消息后先写入 `message_events`，包含 `event_id`、`chat_id`、`user_id`、`raw_text`、`timestamp`。
2. Hermes 输出结构化路由结果：`intent`、`confidence`、`normalized_query`、`entities`。
3. Hermes 超时或低置信时启用规则兜底：报警码、型号、FANUC、机器人、参数、故障等关键词直接触发 RAG。
4. RAG Core 返回结构化结果：`answer`、`sources`、`top_score`、`risk_tags`、`latency_ms`。
5. 日志记录入口判断和 RAG 结果，区分失败发生在入口层还是检索层。

## 3. 不依赖用户显式反馈，改用隐式失败信号

用户在排障场景下不会稳定点击“有用/无用”。当答案没用时，用户更可能失望、追问、改问别人或沉默。因此，反馈飞轮不应依赖按钮，而应从自然行为中识别失败。

优先采集的隐式信号：

| 信号 | 判断方式 | 可能含义 |
| --- | --- | --- |
| 低置信度 | `top_score` 低、无引用、引用分散 | 召回弱或答案依据不足 |
| 追问 | 同一用户短时间内继续问相似主题 | 上一答没有真正解决 |
| 改写 | 用户换说法重新提问 | 系统未理解原始表达 |
| 否定表达 | “不对”“不是这个”“没用”“还是不行” | 明确失败 |
| 转人工 | 用户 @ 专家、问“谁知道”、转发截图 | 系统没有闭环解决 |
| 高频重复 | 多人反复问同类问题 | 高价值优化场景 |
| 能力缺口 | 用户发截图/日志，但系统无法处理 | 输入能力或知识覆盖不足 |
| 超时/异常 | 请求超时、LLM/RAG 报错 | 稳定性问题 |

第一版 `risk_tags` 可以只做规则：

| 规则 | 标签 | 后续动作 |
| --- | --- | --- |
| `top_score < 0.65` | `low_confidence` | 进入 bad case 候选池 |
| 无引用来源 | `no_source` | 检查召回与答案生成链路 |
| 引用超过 4 份且分数接近 | `topic_drift` | 优化分类、实体识别或 rerank |
| 同一用户 5 分钟内相似追问 | `followup_unresolved` | 聚合为同一问题簇 |
| 用户出现否定表达 | `explicit_negative` | 优先进入修复队列 |
| 7 天内相似问题出现 >= 3 次 | `high_frequency` | 优先补文档、规则或 FAQ |
| 用户上传截图但无法解析 | `input_gap` | 后续考虑 OCR / 图片理解 |
| 答案过长但缺少步骤结构 | `poor_actionability` | 优化回答模板 |

## 4. 最小质量飞轮

不要先建设复杂后台，也不要把多维表格变成人工台账。最小飞轮只需要：

```text
query_log
  ↓
risk_tags 自动打标
  ↓
相似问题聚类
  ↓
每周 Top 10 修复清单
  ↓
人工小步修复：规则 / 同义词 / 文档 / chunk / prompt
  ↓
加入 regression_set
  ↓
每日自动巡检
```

建议每周自动生成轻量周报：

```text
本周最值得修复的 10 个问题簇

1. SRVO / SVGN 报警码类问题
- 出现次数：17 次
- 涉及用户：5 人
- 失败信号：低置信度 6 次，疑似追问 8 次，否定表达 2 次
- 疑似原因：报警码归一化不足，部分前缀未进入同义词和分类规则
- 建议动作：补充 SRVO / SVGN / SVALM 等报警前缀规则，加入报警类回归题
- 验证方式：修复后每日巡检覆盖 5 个典型报警码问题
```

维护者每周只处理 Top 问题簇，而不是查看全量日志。

## 5. 并发与稳定性：先做可控，不盲目扩容

当前代码里已有局部并行：向量检索与 BM25 并行，报警码、型号和型号变体搜索并行。下一步不要盲目提高线程数，而应先做入口限流、超时和降级。

初始建议参数：

```text
MAX_INFLIGHT_QUERIES=2
RETRIEVAL_WORKERS=6
ENTITY_SEARCH_WORKERS=3
MULTI_QUERY_WORKERS=2
RERANK_WORKERS=1
REQUEST_TIMEOUT=30s
QUEUE_TIMEOUT=3s
```

如果关闭 cross-encoder rerank、LLM 是远程 API，可以把 `MAX_INFLIGHT_QUERIES` 逐步提升到 4。若本地模型或 reranker 吃 CPU/GPU，先保持 2。

最小任务：

1. 增加入口并发闸门，避免少数慢查询拖死全部请求。
2. 多问题拆分最多并行 2 个子问题。
3. SQLite 日志启用 WAL、`busy_timeout`，并考虑异步日志队列。
4. 高负载时降级：减少 `top_k`、跳过 rerank、只返回检索摘要。
5. 记录分段耗时：`intent_ms`、`vector_ms`、`bm25_ms`、`entity_ms`、`rerank_ms`、`llm_ms`、`total_ms`。

并发压测指标不只看 QPS，还应看：

- P50/P95 延迟。
- 超时率。
- 低分率。
- 无引用率。
- 并发下 `top_score` 是否退化。
- 日志是否丢失。

## 6. 用户感知优化

当前阶段最重要的是让答案“短、准、可执行、可信”。建议优先优化：

1. **低置信度策略**：证据不足时少答，不硬猜；提示需要补充型号、报警截图、控制器版本等。
2. **步骤化答案**：报警排查、通信配置、安全参数等问题优先输出操作路径或排查顺序。
3. **引用可见**：每个关键结论带来源文件，避免用户觉得是模型编的。
4. **继续追问**：回答末尾给出一个自然追问入口，例如“如果能补充型号/截图，我可以继续定位”。
5. **高频缓存**：报警码、型号参数等高频短问可缓存，提升关键场景响应速度。

## 7. 长期路线：能力包而不是网页平台

长期可抽象为：

```text
任意人类通讯 App
  ↓
任意 Agent 智能网关
  ↓
可插拔专业知识库
  ↓
RAG Core + 领域规则 + 质量飞轮
```

当前实现是 `飞书群 + Hermes + FANUC`，但长期可以替换为：

| 层级 | 当前实现 | 长期可替换方向 |
| --- | --- | --- |
| 人类通讯层 | 飞书群 | 企业微信、钉钉、微信、Slack、Teams、Discord |
| Agent 智能网关 | Hermes | 其他 Agent 框架、自研 Agent、工作流 Agent |
| 专业知识库 | FANUC | PLC、设备维修 SOP、工艺参数、制度流程、项目文档 |
| 检索核心 | Chroma + BM25 + rerank | Qdrant、Milvus、Elasticsearch、pgvector |
| 质量飞轮 | bad case、巡检、同义词、回归题 | 通用失败探测与回归机制 |

当前不做：

- 不急于建设网页入口作为主入口。
- 不急于做多租户平台。
- 不急于做复杂管理后台。
- 不急于支持多个通讯软件。
- 不急于把所有参数暴露给非技术用户。
- 不为了插件化牺牲当前 FANUC 场景质量。

路线图：

```text
先把 FANUC 场景做深
  ↓
沉淀 RAG Core、领域规则和质量飞轮
  ↓
抽象 Agent 网关与通讯入口
  ↓
形成可复用的专业知识助手能力包
  ↓
再复制到其他工业知识场景
```

## 8. 一个月内可执行计划

| 周期 | 目标 | 最小交付 |
| --- | --- | --- |
| 第 1 周 | 日志增强与入口可追踪 | `message_events`、`route_decision`、`query_log` 增加入口、用户、会话、分段耗时字段 |
| 第 2 周 | 失败探测 | 实现第一版 `risk_tags` 规则，覆盖低分、无引用、追问、否定、超时 |
| 第 3 周 | Top 问题簇 | 对失败/高频问题做相似聚类，输出每周 Top 10 修复清单 |
| 第 4 周 | 回归与稳定性 | 将修复问题加入 `regression_set`，增加超时、降级和入口并发闸门 |

验收指标：

- 高频报警码与型号查询召回更稳定。
- 低置信度问题能被自动识别。
- 每周能产出 Top 10 修复清单。
- 修复后的问题能进入每日巡检。
- 2-4 个并发请求下系统不崩、不乱答、不丢日志。
- 用户在关键问题上获得更清晰、更可执行、带出处的答案。
