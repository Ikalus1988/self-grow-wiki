## FANUC RTCP 是什么

RAG 命中片段（B-83284CM-2/05「7.远程TCP 功能」、B-83264CM/03「H.可变远程TCP 的设定方法」）确认：

- 用一个**远程用户坐标系**（UFRAME 1~5）+ **远程工具号** 描述那个「固定点」（焊钳电极、变位机销点等）。
- 程序里设 `UFRAME_NUM = n` + 对应的 `UTOOL_NUM`，机器人走直线时自动让 TCP 锁在那一点上。
- 「可变远程 TCP」还要再叠加定位器（变位机）作为协调组，机器人+定位器一起联动补偿。

**它本质是个运动学补偿功能，不是轨迹规划器。** 它的职责是「让某点跟着外部运动不甩」，不是「让某点走多快」。

## RTCP 能不能让轨迹保持匀速

**结论：RTCP 本身不保证匀速，也不阻止匀速。** 两件事是独立的：

| 维度 | 决定因素 | RTCP 影响 |
|------|---------|----------|
| 走不走得直 | RTCP 补偿、外部轴位姿、坐标系标定 | 直接相关 |
| 走多快 | 前瞻段数、ACC、JERK、CNT、$SPEED | 不直接相关 |

RTCP 模式下出现的「不匀速」通常是这几类根因，不是 RTCP 本身的 bug：

1. **前瞻段数不够**：FANUC 默认 lookahead 段数有限，路径密度低时拐点处必须减速。
2. **协调组动限速**：变位机 / 导轨是「协调轴」时，速度取**所有参与轴里最慢的那一个**。远程 TCP 离基座远、转外轴比例大，电机本身的 `MOTN` / `MAX_SPEED` 就把速度压下来了。
3. **JERK 限制**：FANUC R-30iB 之后默认带 jerk limit，拐弯处自动圆滑降速，看着像「不匀速」其实是有意的 S 曲线。
4. **路径段本身不密**：RTCP 再聪明也只能在示教点之间插补，点位之间距离大 → 必须加减速。
5. **CNT 值**：圆滑过渡用得过大，匀速感强但拐弯处同步降速。

## 4. 共同点/工作方式（各chunk原文要点）

手册原文（B-83504CM_05 / B-83574CM_05 / B-83494CM_07）写的是"**参数的切换**"——指的是"在 2 套伺服运动参数之间切换"。这个动作发生在 `Controlled start → MAINTENANCE → MANUAL` 维护模式下，是 FANUC 通用维护流程，**不是"切高惯量"的专属按钮**。我把它简化成"高惯量模式切换 SOP"，过度归因了。

**错误 2：分类粗暴的对照表**

```
自动（R-2000iC） vs 手动（其他）
```

这个二分法掩盖了真实差异：
- R-2000iC：自动

**错误 3：没区分"购买授权"和"启用操作"**

M-3iA/6S 8kg 等型号的"可选购项"明确给出授权代码（A05B-2560-J595 / A05B-2660-J595）。手册说"使用这功能时需要……"，但**没说激活步骤**——而我跳过了这个 gap，把维护模式的通用参数调整流程当成激活 SOP。

3. 架构收敛：Cloudflare 边缘侧注入 (Edge-Side Injection)
为了解决前端 Web Components 导致的布局延迟，以及无编译 MPA 的缓存刷新问题，我们把组件拼接的战场从“用户浏览器”前移到“Cloudflare 边缘节点”。

利用 Cloudflare Workers 的 HTMLRewriter，在静态 HTML 从边缘发往用户手机的瞬间，直接把公共头部和哈希版本号注入进去。

workers/edge-router.js (边缘渲染与版本控制)
JavaScript
const ASSET_VERSION = "20260628_v1";

export default {
  async fetch(request, env) {
    const response = await env.ASSETS.fetch(request);
    const url = new URL(request.url);

    // 如果请求的是 HTML 页面，我们在边缘进行无感知的动态组装
    if (response.headers.get("content-type")?.includes("text/html")) {
      return new HTMLRewriter()
        // 1. 动态注入带有版本号的 CSS，彻底解决缓存不一致问题
        .on("head", {
          element(el) {
            el.append(`<link rel="stylesheet" href="/shared/css/system.css?v=${ASSET_VERSION}">`, { html: true });
          }
        })
        // 2. 在边缘直接把 Header 结构塞进去，拒绝客户端渲染造成的白屏闪烁
        .on("misaka-header", {
          element(el) {
            const isFanuc = url.pathname.startsWith("/fanuc");
            el.replace(generateHeaderHtml(isFanuc), { html: true });
          }
        })
        .transform(response);
    }

    return response;
  }
};

function generateHeaderHtml(isFanuc) {
  if (isFanuc) {
    return `<header class="industrial-header">...</header>`; // 针对厂房优化的直观头部
  }
  return `<header class="geek-header">...</header>`; // 针对个人作品集的双模态头部
}

2. 边缘网关代码实现 (workers/fanuc-gateway.js)
这个 Worker 部署在 Cloudflare，负责处理国内用户的直连请求，并作为双路路由调度器（快轨走 KV，慢轨走本地 RAG）。

JavaScript
// 伪代码：部署于 Cloudflare Workers，路由拦截 /api/fanuc/*
export default {
  async fetch(request, env) {
    const url = new URL(request.url);
    
    // 1. 简单的速率限制与反爬（继承原本的抗自动化思路）
    const clientIp = request.headers.get("cf-connecting-ip");
    if (await isRateLimited(clientIp, env)) {
      return new Response("Too Many Requests", { status: 429 });
    }

    // 路径分流
    if (url.pathname === "/api/fanuc/search") {
      const { query } = await request.json();
      
      // 【快轨】尝试精确命中常见报警码（100ms内返回）
      const alarmCode = parseAlarmCode(query); // 正则匹配 SRVO-023 等
      if (alarmCode) {
        const cachedResult = await env.FANUC_ALARM_KV.get(alarmCode);
        if (cachedResult) {
          return new Response(JSON.stringify({ type: "FAST", data: cachedResult }), {
            headers: { "Content-Type": "application/json" }
          });
        }
      }

      // 【慢轨】穿透隧道调用本地私有 RAG 算力
      // LOCAL_RAG_TUNNEL_URL 是通过 cloudflared 或 frp 映射的边缘地址
      return fetch(`${env.LOCAL_RAG_TUNNEL_URL}/v1/chat/completions`, {
        method: "POST",
        headers: request.headers,
        body: JSON.stringify({
          model: "industrial-rag-fanuc",
          messages: [{ role: "user", content: query }],
          stream: true // 开启 SSE 流式传输
        })
      });
    }
  }
};

🔥 严肃、挑剔的架构师 Review
这套方案看似链路清晰，但如果直接推向生产环境，在真实的工业现场和恶劣的网络环境下，会暴露出几个致命的隐患。以下是我最挑剔的 Review 意见：

❌ 痛点一：算力饥饿与公网暴露的冲突（本地 GPU 会被冲垮）
挑剔审查： 飞书机器人目前之所以“用户留存好且运行稳定”，是因为飞书有天然的封闭性（群聊 @ 机器人、企业内部认证），天然隔绝了公网爬虫。一旦你在 misakanet.org 上开辟了公开的网页入口，全网的搜索引擎爬虫、自动化脚本、甚至同行恶意刷流量的 Bot 就会顺着 Cloudflare Tunnel 直接把请求怼到你本地那台可怜的 RAG 服务器上。本地的显存/算力瞬间就会因并发被榨干，导致飞书端响应同时瘫痪。

落地修正药方： 网页端绝不能做成完全无门槛的开放查询。必须引入“轻量级凭证绑定”。例如：用户必须在飞书群里输入 /webtoken 动态获取一个 24 小时有效的短 Token，在网页端输入 Token 后激活浏览器 Session。用飞书的闭环生态来保护本地有限的硬件算力。

❌ 痛点二：工业断流与 SSE（流式传输）的断裂灾难
挑剔审查： 现场工程师拿着手机在厂房深处、行车下方、或者屏蔽严重的设备夹层里看对比选型（如 360 机器人 VS 700 机器人速度），网络信号可能只有微弱的 1-2 格。大模型流式生成的 SSE（Server-Sent Events）长连接在这种高丢包率、随时断流的基站环境下体验极差。频繁的连接中断会导致前端渲染出“半截 Markdown 表格”或卡死。

落地修正药方：

强推本地降级： 仿照十年前那个 ASP.NET 站点的精髓，把最核心、最救命的 2000 个常用报警码索引及其 SOP 处理方法，直接打包成一个不到 2MB 的压缩 JSON，随前端静态页面一次性下载到浏览器，或者缓存在 Cloudflare Edge KV 中。

当现场网络极差、穿透本地 RAG 超时时，前端立刻切断慢轨，100% 降级为纯本地/边缘离线查询，确保“报警排查”这个最刚需的模块永远具有秒开、不中断的绝对高可用性。

❌ 痛点三：完全去依赖（Zero-Dep）带来的前端“屎山”风险
挑剔审查： 我非常赞同你网页端不使用 React/Vue 等重型框架的洁癖，但在 2026 年，如果完全用 Vanilla JS 去手写流式 Markdown 解析（将 RAG 返回的流实时渲染成结构化的硬件针脚对比表格、高亮警报卡片），代码中会充斥着大量的 innerHTML、字符串拼接和复杂的 DOM 手动操作。这不仅难以维护，而且极易引入 XSS 漏洞。

落地修正药方： 保持不引入运行时框架的底线，但前端必须引入一个极轻量、单文件、无编译步骤的声明式渲染微库（例如 Alpine.js，大小仅十几 KB）以及一个安全的静态 Markdown 解析器（如 marked.js）。用数据驱动（Data-Driven）的方式去处理“硬件查询”与“对比选型”的结构化渲染，优雅地保持代码的可读性。
