# 面向通讯场景的专业知识 RAG：工程收敛复盘

## 背景

专业知识 RAG 常见落地方式是网页问答、文档搜索或 Bot 入口。但在现场协作型场景里，用户往往已经处在 IM 群聊、工单、协作群或专家群中。要求用户切换到一个网页入口，未必符合真实工作流。

更自然的形态是：

```text
人类通讯 App
  ↓
Agent 智能网关
  ↓
专业知识 RAG
  ↓
带出处、可执行、可追问的答案
  ↓
使用痕迹驱动质量飞轮
```

本复盘总结的是一类通用经验，不绑定具体公司、品牌、文档或账号。

## 关键结论

1. **群聊入口不是落后形态**：在协作和排障场景中，IM 入口比网页入口更贴近用户工作流。
2. **Agent 网关不只是转发器**：它应负责意图判断、上下文补全、工具路由、低置信度追问和异常兜底。
3. **不要依赖用户显式反馈**：用户在压力场景下不会稳定点击“有用/无用”，失败信号应从自然行为中提取。
4. **并发不是早期首要矛盾**：在真实使用量未上来前，优先做可控并发、超时、降级和日志完整性。
5. **插件化是长期路线**：先把单一领域做深，再沉淀 RAG Core、领域规则、Agent 网关和质量飞轮。

## 优先级判断

| 优先级 | 问题 | 原因 | 最小动作 |
| --- | --- | --- | --- |
| P0 | 智能入口可靠性 | 入口异常会让用户在关键时刻认为系统不可用 | 消息落盘、规则兜底、异常可追踪 |
| P0 | 失败不可感知 | 用户失败后常沉默、追问或换人问 | 用隐式行为自动打 `risk_tags` |
| P1 | 答案可信与可执行 | 专业场景中无出处、硬猜测会破坏信任 | 强制引用、低置信度少答、主动追问上下文 |
| P1 | 稳定性与降级 | 用户可以接受慢一点，不能接受卡死或乱答 | 超时、限流、降级、失败日志 |
| P1 | 维护成本 | 人工翻全量日志无法长期持续 | 聚合 Top 问题簇，每周小步修复 |
| P2 | 高并发 | 早期更像容量问题，不是第一矛盾 | 2-4 并发稳定后再压测扩容 |
| P2 | 跨场景复用 | 需要建立在单一领域跑稳后 | 抽象领域包和质量飞轮 |

## 架构经验

推荐职责划分：

```text
消息接收层
  - 接收 IM 事件
  - 原始消息先落盘
  - 保证可回放、可排查

Agent 智能网关
  - 判断闲聊 / 查询 / 追问 / 反馈 / 转人工
  - 提取实体和上下文
  - 选择是否调用 RAG
  - 异常时交给规则兜底

规则兜底层
  - 命中领域关键词、编号、型号、错误码等时直接触发 RAG
  - 避免 Agent 判断超时导致请求丢失

RAG Core
  - 检索、rerank、生成、引用
  - 低置信度策略
  - 记录 query_log 和 risk_tags

质量飞轮
  - 失败探测
  - 问题聚类
  - 周报
  - 回归验证
```

## 隐式反馈优先于显式反馈

显式反馈按钮可以保留，但不能作为主燃料。更可靠的失败信号包括：

| 信号 | 判断方式 | 可能含义 |
| --- | --- | --- |
| 低置信度 | 检索分数低、无引用、引用分散 | 召回或证据不足 |
| 追问 | 同一用户短时间内问相似主题 | 上一答未解决 |
| 改写 | 换说法重新提问 | 意图理解或召回失败 |
| 否定表达 | 出现“不对”“不是这个”“没用”等 | 明确失败 |
| 转人工 | @ 专家、问“谁知道”、转发截图 | 系统未闭环 |
| 高频重复 | 多人反复问同类问题 | 高价值场景 |
| 超时异常 | 请求超时、生成失败、入口异常 | 稳定性问题 |

第一版 `risk_tags` 不需要复杂模型，规则即可起步。

## 最小质量飞轮

```text
query_log
  ↓
risk_tags 自动打标
  ↓
相似问题聚类
  ↓
每周 Top 10 修复清单
  ↓
人工小步修复
  ↓
加入 regression_set
  ↓
每日自动巡检
```

关键原则：

- 不建设复杂后台。
- 不让维护者翻全量日志。
- 不要求用户额外标注。
- 每周只处理少数最值得修的问题。
- 修复后的问题必须进入回归集。

## 并发与稳定性

早期不要直接追求高 QPS。更合理的目标是：少量真实用户同时查询时，系统不崩、不乱答、不丢日志。

可从以下参数起步：

```text
MAX_INFLIGHT_QUERIES=2
RETRIEVAL_WORKERS=4~8
ENTITY_SEARCH_WORKERS=3
MULTI_QUERY_WORKERS=2
RERANK_WORKERS=1
REQUEST_TIMEOUT=30s
QUEUE_TIMEOUT=3s
```

观测指标：

- P50/P95 延迟。
- 超时率。
- 无引用率。
- 低置信度比例。
- 并发下答案质量是否退化。
- 日志是否完整。

## 长期复用方式

长期可以抽象成能力包，而不是先做复杂平台：

```text
任意人类通讯 App
  ↓
任意 Agent 智能网关
  ↓
可插拔专业知识库
  ↓
RAG Core + 领域规则 + 质量飞轮
```

复用时替换：

- 文档集合。
- 领域规则。
- 典型问题。
- 通讯入口。
- Agent 网关。

保留：

- 混合检索与引用回答。
- 低置信度策略。
- 风险标签。
- bad case 聚类。
- 周报和回归验证。

## 反模式

避免以下做法：

- 过早建设网页主入口，忽视用户已经所在的通讯场景。
- 把反馈按钮当作质量飞轮核心。
- 一开始就做复杂后台、多租户、多入口。
- 为了并发提前复杂化，而没有超时、降级和日志。
- 在单一领域还没跑稳前急于平台化。
- 把所有参数暴露给非技术用户。

## 一个月最小行动计划

| 周期 | 目标 | 最小交付 |
| --- | --- | --- |
| 第 1 周 | 入口与日志可追踪 | 原始消息落盘，记录路由决策、用户、会话、分段耗时 |
| 第 2 周 | 失败探测 | 实现 `risk_tags`，覆盖低分、无引用、追问、否定、超时 |
| 第 3 周 | 问题聚类 | 聚合失败和高频问题，生成 Top 10 修复清单 |
| 第 4 周 | 回归和稳定性 | 修复项加入回归集，增加超时、降级、入口并发闸门 |

## 可迁移判断

当遇到新的专业知识问答需求时，可以用以下问题判断是否适用本模式：

1. 用户是否已经在某个通讯场景里协作？
2. 问题是否需要专业文档、出处和可执行步骤？
3. 用户是否很难通过官网搜索或通用搜索获得完整答案？
4. 失败是否可以从追问、改写、低分、无引用、转人工等行为中观察到？
5. 维护者是否能每周处理少量 Top 问题，而不是全量运营？

如果答案大多为是，优先考虑“通讯场景 + Agent 网关 + 专业 RAG + 质量飞轮”的架构。
